# Zig binding: notes

## Approach

Raw CPython C API through `@cImport("Python.h")`, plus a small reusable comptime layer
(`src/py.zig`). That layer reflects over plain Zig declarations with `@typeInfo` and generates
the extension module and its `.pyi`. `src/aigame.zig` holds only the module's API and reads
roughly like the stub:

```zig
pub const Vector2 = struct { x: i32, y: i32 };
pub fn update(a: struct { mouse: Vector2, click: bool, reset: bool }) GameState { ... }
pub fn init(a: struct { render: bool = true }) void { ... }
comptime { py.exportModule(@This(), "aigame"); }
```

`src/game.c` is compiled unchanged as a C source by `build.zig`. Its types come from
`@cImport("game.h")`. Static `libraylib.a`, `libglfw3.a` and `-lm` are linked into `aigame.so`.

## ziggy-pydust

I did not use it. Its `pyproject.toml` on `develop` pins `ziglang = "^0.15.1"`. The last release
is 0.26.0 (2025-09-18). Commits since then are dependency lock-file bumps only. Nothing supports
0.16, so it would need a port to the 0.16 build and std APIs. Pydust also drives the build from
Python (poetry or a build hook), not from a plain `zig build`.

## What comptime does vs what stays manual

Generated by `py.zig` from the declarations:

- **Classes.** Each class gets:
  - a `PyTypeObject`;
  - an `extern` storage struct built with `@Struct`: a `PyObject` header plus one slot per field. `i32` and `bool` are stored inline; any other type is stored as an owned `PyObject*`;
  - a `PyMemberDef` table: `T_INT`, `T_BOOL` or `T_OBJECT_EX`, with offsets from `@offsetOf`;
  - `tp_dealloc`, which DECREFs the object slots;
  - `__init__` with positional and keyword arguments;
  - a dataclass-style `__repr__`, which gives `Vector2(1, -2)`;
  - `__reduce__` for pickling.
- **Functions.**
  - Each gets a `METH_FASTCALL | METH_KEYWORDS` wrapper, or `METH_NOARGS` when it takes no arguments.
  - Arguments are parsed from the fields of the args struct, so names come from field names and defaults from field initialisers.
  - Error messages: too many arguments, duplicate argument, unknown keyword, missing argument.
- **Conversions.**
  - `i32`: range-checked; `OverflowError` when out of range.
  - `bool`: truthiness via `PyObject_IsTrue`, the same as PyArg `"p"`.
  - `[N]T` ↔ `list`.
  - struct ↔ class.
  - `void` → `None`.
- **Signatures.** Docstrings start with `name($module, ...)\n--\n\n`, so `inspect.signature(aigame.init)` returns `(render=True)`.
- **Module setup.** `PyInit_aigame` (exported with `@export`), the module def, the method table, `PyType_Ready`, and int constants.
- **The `.pyi` stub** (see below).

Written by hand in `aigame.zig`:

- **Constants.** `game.h` defines them as doubles (`#define SCREEN_WIDTH 800.`), so they need `@intFromFloat`.
- **Vector2 conversion.** raylib's `Vector2` is float and the Python `Vector2` is int, so `toC`/`fromC` convert between them. The cell maths copies `pylib.c`.
- **Building `GameState` from `State`.** This is the actual binding logic.
- **Docstrings.** They go in `pub const __doc__ = .{ .update = "..." }` because Zig doc comments cannot be read at comptime.
- **Arguments.** Each function takes one args struct, because `@typeInfo(fn).params` has types but no names. A struct gives names and default values. This is the main place the source differs from a 1:1 Python signature.

## translate-c friction (Python 3.10 headers, Zig 0.16)

What `@cImport` produced for macros:

| Macro | Result |
|---|---|
| `PyModuleDef_HEAD_INIT` | `error: unable to translate C expr: unexpected token '{'` |
| `PyObject_HEAD_INIT`, `PyVarObject_HEAD_INIT` | same `unexpected token '{'` |
| `PyObject_HEAD` | `unable to translate macro: undefined identifier 'ob_base'` |
| `Py_RETURN_NONE` | `unable to translate C expr: unexpected token 'return'` |
| `PyList_SET_ITEM` | `unable to translate C expr: expected ')' instead got '='` |
| `PyMODINIT_FUNC` | translated to nonsense (`[*c](Py_EXPORTED_SYMBOL ++ PyObject)`) |
| `Py_None`, `Py_True`, `Py_False` | become inline *functions*, so you write `c.Py_None()` |
| `PyTuple_GET_ITEM` | translates, but indexes `ob_item: [1][*c]PyObject`, so any `i > 0` is out of bounds by Zig's rules |

Workarounds, about 10 lines in total, all in `py.zig`:

- A `head_init: PyObject = .{ .ob_refcnt = 1, .ob_type = null }` constant, plus `std.mem.zeroes(PyTypeObject)` with field assignment instead of the brace initialisers.
- An explicit `ob_base: PyObject` first field instead of `PyObject_HEAD`.
- `inc(c.Py_None())` instead of `Py_RETURN_NONE`.
- The function forms `PyList_SetItem` and `PyTuple_GetItem` instead of the macros.
- `@export` instead of `PyMODINIT_FUNC`.

What worked without changes: `Py_INCREF`/`Py_DECREF`/`Py_XDECREF` and `Py_TYPE` (static inlines), `PyObject_TypeCheck`, `PyList_Check`, `PyModule_Create`, the `T_*` and `METH_*` constants, `Py_TPFLAGS_DEFAULT`, and the variadic `PyErr_Format` / `PyUnicode_FromFormat` / `Py_BuildValue`.

The FASTCALL function pointer needs an `@ptrCast` to the `PyCFunction` type, the same as the cast C makes.

## How the stub is produced

- `py.stub(M)` builds the `.pyi` text at comptime from the same declarations.
- `build.zig` builds `src/stubgen.zig` for the host. It is a 4-line exe that writes that comptime string to stdout. `captureStdOut` collects the output and installs it as `aigame.pyi`.
- `py.exportModule` checks `builtin.output_mode`, so the exe does not export `PyInit_*`. The exe also never calls the wrappers, so it needs neither libpython nor raylib at link time.
- The generated stub has plain classes with typed fields and `__init__`, not `@dataclass`, because the types have no `__eq__`.
- Checked with pyright: the typed uses type-check and the bad calls are flagged.

## Build times

Measured with `make` in `bindings/zig`, ReleaseFast.

| Case | Time |
|---|---|
| Cold: empty global cache (`ZIG_GLOBAL_CACHE_DIR` pointed at a fresh dir) and empty local cache | 62.4 s |
| Clean: `make clean` (local `.zig-cache` and output removed), warm global cache | 2.4 s |
| Incremental: edit a string in `aigame.zig` | 0.6–0.7 s |
| No-op | 0.06 s |

Most of the cold time goes to Zig building its own libc/compiler-rt pieces and the build runner, which happens once per machine.

## Results

- All 22 conformance tests pass in ReleaseFast. They also pass in Debug, which has Zig safety checks and UBSan on `game.c`.
- `aigame.so` is 1.51 MB; the c_capi build is 1.41 MB.

## Surprises

- `@typeName(T)` of a top-level decl is `"<file stem>.<Decl>"`, so `tp_name` comes out as `aigame.Vector2` without extra work. Pickling depends on that name. It does tie the module name to the file name `aigame.zig`.
- `-ffp-contract=off` on `game.c` is defensive only. clang contracts a*b+c into FMA on this FMA-capable CPU and gcc does not, but the golden trace matched either way.
- Compared with `pylib.c`, the binding accepts more:
  - every function also takes keyword arguments;
  - `GameState` gets `__init__`, `__repr__` and `__reduce__`;
  - the error message texts are different.
- No conformance test depends on any of these differences.
- `bool` parameters are typed `bool` in the stub, but at runtime they take any truthy value, the same as `"p"` in the C baseline.
- Two 0.16 API changes:
  - The build API: `standardOptimizeOption(.{ .preferred_optimize_mode = ... })` turns off `-Doptimize`; it expects `-Drelease`.
  - The std API: `main` takes `std.process.Init`, and stdout is written with `std.Io.File.stdout().writeStreamingAll(io, ...)`.
